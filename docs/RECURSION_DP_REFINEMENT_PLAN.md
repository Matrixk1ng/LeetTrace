# Recursion and dynamic programming refinement

Status: approved and implemented locally. The user rejected
the path/choose/undo concept as confusing and requested a nested call walkthrough
with returned values and memo reuse, plus a distinct bottom-up presentation.

[Open interactive preview](./previews/recursion-dp-refinement.html).

## Implemented scope

- General recursion: separate invocation identities, indented calls/returns,
  foldable calls with returned-answer summaries, active-call context, optional
  follow, parameter details, and previous/next event jumps into exact snapshots.
- Memo: observed direct dictionary assignments and direct stored-value returns.
  Reuse requires a matching prior save from another invocation and no child
  expansion in the returning invocation. A just-computed return is not a hit.
  Recorded saves are historical evidence; current containers remain inspectable.
- Bottom-up: one-dimensional builtin lists with assignments adding two entries
  from that same list. Displays actual values (including zero/None), source and
  destination indices, before-write versus completed-write equation, recent
  confirmed writes, and index inspection for large tables.
- Python inspects a bounded safe AST subset; it never evals user expressions or
  invokes custom container/index methods. Exceptions cancel pending assignments.
  Same-line ambiguity, custom containers, containers over 2,000 entries, and
  unsupported expressions keep ordinary views. Rendering is bounded to 300 call
  events, 30 saved entries, 24 table cells, and 12 recent table writes.
- The richer table view begins once an eligible recurrence assignment is reached.
  Earlier initialization uses the existing array renderer. General memo
  decorators, multidimensional DP, other recurrence operators, inferred base-case
  explanations, and automatic equations for recursive return combinations remain
  separate refinements. No memo toggle or approach switch rewrites user code.

## Top-down: calls, answers, optional memo

Use the user's recurrence example: f(0) = f(1) = 1, f(5) = 8. Indentation and
branch guides show caller/child relationships. Every call has its own identity,
including repeated calls with equal arguments. Display base cases, child-result
combination, explicit memo writes, observed reuse, and returned values within the
owning call. Completed call headings summarize their answer; calls can fold.
Keep the active event in view with an optional follow control.

Saved answers appear in a small supporting table. A cache hit produces a new call
that returns a saved value without expanding children. Merely having a matching
key is not proof of reuse. The preview's memo toggle runs a separate illustrative
walkthrough without caching; it does not modify user code. Base cases are not
stored by this example. Rewind shows only the reached prefix of calls and writes.

## Bottom-up: dependencies and table writes

Use a table rather than a call tree. Show base-case initialization, then highlight
the two cells being read and the destination being filled. The equation connects
their values to the destination. Distinguish before-write (unknown target) and
completed write. A compact history lists only entries filled so far.

The same f(5) example makes the two approaches easy to compare. The production
renderer must follow actual iteration and indexing, not assume left-to-right
order, two operands, Fibonacci recurrence, or that zero means unfilled. This
preview deliberately initializes with None to make unknown entries explicit.

## Implementation sequence and follow-up criteria

1. General recursion first: nested call/return history with entry parameters and
   actual returned values, independent of tree-node inputs or DP classification.
   Preserve stable call identity, exact stepping, and bounded rendering for deep
   or large traces. Inspecting a folded call must remain keyboard accessible.
2. Memo enhancement: prove lookup/return reuse and explicit writes from source
   metadata and observed execution; retain generic calls when ambiguous. Cached
   decorators, multidimensional keys and mutable values need separate audits.
3. Bottom-up DP as a separate slice: trace-backed dependencies and write effects,
   starting with clear one-dimensional table assignments. Unknown dependencies
   fall back to the existing array/grid view, without invented equations.
4. Validate with real memoized and plain recursion, repeated arguments, early
   returns, rewind, zero/False values, and loop initialization/read/write boundaries.
   Review real app renders at 400px and 550px after each bounded slice.

Traditional backtracking (Subsets/Permutations choose and undo) remains deferred;
the recurrence walkthrough is not a replacement detector for those algorithms.
The current preview uses illustrative events, not production semantic inference.
